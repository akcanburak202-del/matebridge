## Amaç

Today the tablet trusts any endpoint that answers PAIRING: it overwrites the stored pair key at the first PAIRING ack and opens input, clipboard (both ways), audio and the FILES_INFO WebDAV token as soon as a sealed ACCEPTED arrives, with no local check. A fake Mac found by Bonjour, anyone answering at the remembered IP, or a tablet app squatting `127.0.0.1:47001` therefore gets every keystroke (passwords included) and full read/write access to shared storage, and a same-`host_id` impostor locks the real Mac out in an endless PROTOCOL_ERROR loop. This card moves the trust decision onto the tablet: a new key stays **pending** until the user confirms the code, the session opens only when the host accepted **and** the key is locally trusted, and pairing only ever starts from a user action. This is the core security fix of D2. The AUTO-mode USB migration gate (A2 side finding, scenario 4 below) was split out by QA-1 into T-205, which depends on this card.

## Bağlam

`C/` = `client-android/app/src/main/kotlin/dev/matebridge/client/`. Lines are at HEAD a30c769 and were re-checked.

**Evidence: the key is overwritten before any local step**
- `C/security/Handshake.kt:131-149` `ClientHandshake.complete`: for `KEY_PAIRING` the stored key only sets `rePairing` (:141). It is not an input to the KDF (:142) and is zeroed (:144).
- `Handshake.kt:67-77` `SecureSession.storePairKey` → `store.put(hostId, newPairKey)`, once, no compare. `C/security/PairKeyStore.kt:38-41` writes the single `pairkey.<hostIdHex>` entry in place. There is no pending slot, no `remove`, no compare.
- `C/session/SessionController.kt:662-677` (reader thread): `storePairKey` runs right after the first plaintext PENDING ack (:666, comment :665 says this is intended), **before** `Secured` (:676) and `Received` (:677) are posted. No UI or user step comes first.
- PROTOCOL.md §9 "Eşleşme" bullet 3 and "Bağlantı koptuktan sonra onay" (1) mandate exactly this ("hemen saklar (eskisinin yerine)"), as does T-044. It is a design flaw, not a bug.

**Evidence: a sealed ACCEPTED opens everything**
- The fake host did the ECDH, so it holds `controlH2c` and can seal ACCEPTED. `C/session/SessionMachine.kt:299-320` `onAck(ACCEPTED)` queues PING, STREAM_PREFS, DISPLAY_RATE, AUDIO_PREFS and FILES_INFO (:306-310), sets `Phase.ACCEPTED` (:316) and emits `Connected` (:317). `inputAllowed` (:166) becomes true.
- Input: `SessionController.trySend`/`trySendInput` gate only on `inputAllowed` (:278-295). Inbound CLIPBOARD: `SessionController.kt:367` (gated only on `inputAllowed`) → `setPrimaryClip`. Outbound clipboard follows `render(Connected)` (`C/MainActivity.kt:1860-1863`). SETTINGS_OPEN: `SessionMachine.kt:283`.
- Audio: AUDIO_CONFIG/AUDIO_FRAME go from the reader straight to the listener with no acceptance check at all (`SessionController.kt:728-737`, `deliverAudio` :748-758). A fake host can play audio on the tablet even before ACCEPTED.
- The SAS is display-only: `MainActivity.kt:2053-2070` `pairingText` has no button; `SessionUi.AwaitingApproval` (`C/session/SessionUi.kt:12`) has no confirm state.

**Failure scenarios this card must close (A, A2)**
1. **Auto-discovered fake host.** On the Wi-Fi path (WIFI mode, or AUTO after the USB probe closed; `MainActivity.kt:1513-1537`), `MacDiscovery` connects to every resolved `_matebridge._tcp` IPv4 service (`C/session/MacDiscovery.kt:105-122`) and `onDiscovered` calls `connect(ep)` whenever the tablet is Searching or Disconnected (`MainActivity.kt:1803-1809`; `C/session/WakeConnect.kt:127-134`). The remembered `lastWifiEndpoint` is retried directly (`MainActivity.kt:274`, `:1536`). The attacker sends PENDING(PAIRING) and a sealed ACCEPTED in one write, with any `host_id`; the code screen flashes or never paints; the tablet shows "connected" to the attacker's `hostName`. Nothing appears on the Mac.
2. **Localhost squatter gets the WebDAV token** (A2 §2). In AUTO (the default) an un-gated TCP probe to `127.0.0.1:47001` runs on every `applyTransport` (`MainActivity.kt:1524`, `:1597-1625`; OPEN → `startUsb` :1632-1634) and USB mode always connects there (`:1540-1548`; `C/session/ConnectMode.kt:14-18`). Any app with INTERNET can bind that port whenever `adb reverse` does not hold it. It completes PAIRING, seals ACCEPTED and decrypts FILES_INFO(READY, port, token) (`SessionMachine.kt:310`; published by `C/files/FilesController.kt:79-99` whenever the server listens). With the token, DigestAuth grants full DAV read/write on `/sdcard`. This breaks decision 0015 item 3 ("tabletteki başka uygulamalar localhost üzerinden dosyalara erişemez").
3. **Same-`host_id` overwrite → DoS.** The overwrite happens at the first ack even without ACCEPTED. The next PAIRED connection to the real Mac derives with the wrong key, the first host record fails AEAD → `lose(PROTOCOL_ERROR)` (`SessionMachine.kt:211-216`) → retry forever.
4. **Migration on a plaintext ack** (A2 side finding; audit §4.7): **moved to T-205.** This card only keeps today's rule that a candidate never pairs (`candidateKeys.put` throws, `SessionController.kt:154-161`; a PENDING ack aborts, `SessionMachine.kt:465`) and must not make that path store or pend anything.

**Design (decision 0018 option (c)); the implementer may refine names, not semantics**
- **Store.** Trusted record unchanged: `pairkey.<hostIdHex>` = wrap(key, aad = hostId) (no migration of existing keys). New pending record: `pairpend.<hostIdHex>` = wrap(key(32) ‖ sas(6 ASCII digits) ‖ createdAtWallMs, aad = hostId ‖ "pending"). `PairKeyStore` gains `getPending/putPending/promote/dropPending/remove`. `promote` is **one** atomic commit: write the trusted record (re-wrapped with aad = hostId), remove the pending one and write the *awaiting-host marker* (below) in a single `SharedPreferences.Editor.commit()`. That needs `remove` and a multi-key commit. **New `KeyValueStore` methods get default bodies** (e.g. `remove` and the multi-key commit throw `UnsupportedOperationException`), **or** they go on a separate interface (e.g. `AtomicKeyValueStore : KeyValueStore`) that only `EncryptedPairKeyStore` requires. No other implementer changes: the test fakes outside `files:` (`test/.../input/InputSupportTest.kt:16`, `test/.../stream/GameModeTest.kt:17`, `test/.../stream/StreamModeTest.kt:11`) and the settings adapter `MainActivity.kt:455` must compile untouched. The Android implementation that gets the new methods is the pair-key object at `MainActivity.kt:472-480` (this object and the compile-only branches below are the only `MainActivity.kt` changes in this card). The SAS is a secret like the key: wrapped, never logged.
- **Pending expiry (wall clock).** A pending record older than `PENDING_MAX_AGE` (default 10 min of wall-clock time, well past the Mac's 2-min orphan window), or with a timestamp in the future, is **stale**: it is dropped when read and never shown. A PAIRED ack with only a stale pending record derives with the trusted key as today. This stops a forgotten or attacker-made pending record (e.g. the user tapped "Eşleş" for an impostor using the real `host_id` and left without "İptal") from later hijacking the silent reconnect to the real Mac. Record N in Handoff for 0018.
- **Awaiting-host marker.** A local confirm promotes at once (needed for "confirm before leaving for Parsec"), but the Mac may not have approved yet. `promote` therefore also writes a non-secret marker `pairwait.<hostIdHex>` = createdAtWallMs. It is cleared by the first authenticated host record from that `host_id` (and not written when one was already seen on the current connection, i.e. host ACCEPTED came first), by REJECTED, by `forgetCurrentHost()`, and it expires after `PENDING_MAX_AGE` like a pending record.
- **Handshake / reader.** `storePairKey` becomes `storePending` at the same point (`SessionController.kt:663-670`), but **only when the connection is user-initiated**. On a non-user-initiated connection a PAIRING ack is aborted right there: nothing is stored, no SAS is surfaced, the connection is closed, records that may follow the ack are never decrypted or processed, and the machine emits `SessionUi.PairingNeedsUser(hostName, rePair)` (`rePair` = a trusted key exists for that `host_id`). In `complete()`, a PAIRED ack for a `host_id` that has a **fresh** (not stale) pending record must **never** derive with the pending key (nor silently with an older trusted key): return a distinct outcome so the machine shows the stored code for confirmation (see the orphan criterion) and reconnects only after the user decides.
- **`userInitiated`.** `SessionController.start(endpoint, wake, userInitiated = false)` (`SessionController.kt:203`) → `Event.Start(…, userInitiated)`. It holds for the automatic retries of that same start until ACCEPTED, Cancel or Stop. The MainActivity call sites (`connect` at `MainActivity.kt:1850-1857`, called from :1536, :1548, :1807 and :1836, and the wake attempt's direct `controller.start` at :1990) are changed in T-151, not here.
- **No automatic connect while a pairing is unresolved (return before the Mac approved; QA-1 T-150 #1).** Today `onStop` → `controller.stop()` (`MainActivity.kt:1781`) and `onStart` → `applyTransport()` (`:1501`) reconnects at once. After this card that reconnect is `userInitiated = false`; if the Mac has not approved yet it answers PAIRING, and any new PAIRING request cancels the Mac's open orphan window and replaces its key (host `SessionMachine.swift:683-687`). The tablet would then hold key A (pending or already confirmed) while the Mac's dialog shows key B: approving B in Parsec gives an endless mismatch. Rule, enforced in the controller/machine (not only in MainActivity) so it is tested: while a **fresh pending record or a fresh awaiting-host marker** exists, `start(…, userInitiated = false)` opens **no** connection (no HELLO) and the machine emits a connection-less state `SessionUi.StoredTrust(code, confirmed)` instead (`confirmed = false`: pending, show the stored code; `confirmed = true`: marker only, no code). The machine keeps the endpoint of the latest blocked start. The connection that follows a user action on that state ("Kodlar aynı — Güven" → promote, then connect; "Yeniden eşleş"; "Bağlan") goes to that endpoint (T-151 may pass another one for a typed "Bağlan") and is `userInitiated = true`, so if the Mac still answers PAIRING, the new key replaces pending and the new code shows on both sides.
- **Machine.** Track `hostAccepted` and `locallyTrusted` (or a phase `HOST_ACCEPTED_UNTRUSTED`). `inputAllowed` requires both. New events `TrustConfirmed(gen)` and `TrustCancelled(gen)`; controller entry points `confirmTrust()`, `cancelTrust()` and `forgetCurrentHost()` (removes the trusted record, the pending record and the awaiting-host marker of the `host_id` of the last PAIRED ack, the last locally trusted session, or the stored prompt currently shown, in this process; never a `host_id` taken only from an aborted PAIRING answer, which the answerer chooses; returns false when none is known; used by T-151's "Bu Mac'i unut" and T-156's recovery text). While accepted-but-untrusted: only PING goes out; the UI stays `AwaitingApproval(needsLocalConfirm = true, code)` and is **never** `Connected` (so MainActivity neither hides the panel, opens input capture nor starts outbound clipboard). Keep PINGs running: the client pings every 500 ms in PENDING/ACCEPTED (`SessionMachine.kt:356-369`) and the host's silence limit is 5 s, so the host tolerates the wait; no host "video must open" watchdog was found (re-checked on the device in T-157).
- **Trust never flips true→false on an open connection (QA-1 T-150 #3).** `dropConnection()` is a no-op when `!inputAllowed` (`SessionController.kt:302-305`, "the host holds nothing then") and `trySend` refuses everything then, so clearing `locallyTrusted` on a live session could strand an up event or RELEASE_ALL and leave a key or pen stuck on the Mac (AGENTS.md hard rule). Therefore `forgetCurrentHost()` on a live session first ends it like Stop (graceful BYE + close; the host releases all input, PROTOCOL §7), then removes the records, and the machine goes to Idle. No state may exist where `inputAllowed == false` while the control connection that carried a down is still open.
- **Cancel, timeout and REJECTED (QA-1 T-150 #4).**
  - `cancelTrust()` and the local-confirm timeout: if a connection is open, graceful BYE + close; the pending record is deleted; the trusted record is unchanged; the UI goes to `Failed(PAIR_CANCELLED)` (new `SessionUi.Cause`), which is **terminal**: no automatic retry (AUTO sees `FAILED`), until any user start (including "Bağlan"). That stops a mismatch loop when the Mac had already approved: after "İzin ver" (sealed ACCEPTED seen, or unknown as in the orphan flow) the Mac holds the cancelled key, so the next PAIRED connection fails with the old trusted key (or ends in `KEY_MISSING` without one); T-156 bounds that path in `KEY_MISMATCH`. T-151's text for `PAIR_CANCELLED` tells the user to click "Reddet" in the Mac's window, or "Onaylı cihazları unut" in the Mac menu if they already clicked "İzin ver".
  - REJECTED **before** a local confirm deletes pending. REJECTED **after** a local confirm leaves the promoted key (harmless: the Mac stores nothing and answers PAIRING next time) and clears the awaiting-host marker.
- **Local-confirm timeout (2 min): owned by the machine (QA-1 T-150 #7).** The UI posts `Event.ConfirmPromptVisible(visible: Boolean)` (through a controller entry point) whenever a confirm prompt (live `AwaitingApproval(needsLocalConfirm = true)` or `StoredTrust`) becomes visible or hidden; `onStop` always posts `visible = false`. The machine counts the 2-min deadline on Tick **only while visible** (accumulated visible time) and then acts like `cancelTrust()` with `reason=timeout`. Background time never counts; the wall-clock `PENDING_MAX_AGE` covers that. T-151 posts the event.
- **Buffered STREAM_CONFIG.** The host sends STREAM_CONFIG once at ACCEPTED; `onConfig` drops it unless ACCEPTED/STREAMING (`SessionMachine.kt:340-341`). Buffer the latest one and apply it after confirmation; video opens only then.
- **Gates moved to tested code.** `SessionController` has no JVM test today, so the inbound CLIPBOARD gate (:367), the audio gate (:728-758), SETTINGS_OPEN and the reader's user-initiated abort must be decided in the machine or in small pure helpers that the tests drive.
- **Orphan flow on return.** A fresh pending record found when the app returns is shown again with its stored code (`StoredTrust`) and is not dropped merely because background time passed: the orphan flow (see the code → Home/Parsec → "İzin ver" on the Mac → return; NOTES 2026-09-30 l.253) depends on it, and the Mac keeps its own window for 2 min. Only `PENDING_MAX_AGE` drops it. Record the exact rules (2-min visible timeout, `PENDING_MAX_AGE`, marker) in Handoff so the orchestrator can mirror them in 0018.
- **Migration gate:** split out to T-205 (QA-1 T-150 #6). Do not change the candidate promotion order or `MigrationTest.successfulMigrationRetiresThenPromotesThenProvesFirst` here beyond what the new trust flags require.
- **Compile-only edits outside the core files.** The new `SessionUi` subtypes (`PairingNeedsUser`, `StoredTrust`) break the exhaustive `when`s in `MainActivity.applyStatusText` (`MainActivity.kt:1893-1909`), `AutoUsbPolicy.stageOf` / `onProbeOpen` (`AutoTransport.kt:243-248`, `:265-269`) and `WakePlanner.reached` (`C/session/Wol.kt:361-365`), and the new `Cause.PAIR_CANCELLED` breaks `MainActivity.causeText` (`:2087-2098`). Add the minimal mapping only: plain status text; `WAITING_USER` / `IGNORE`; `reached = true`. T-151 owns the real UI. No other change in those three files.
- **Not changed here (residual, documented for 0018):**
  - The normal non-candidate PAIRED connection still goes ACCEPTED on the plaintext ack (`SessionMachine.kt:302-317`). Nothing leaks there: everything the tablet sends is sealed under `pair_key`, so a squatter only gets ciphertext and then fails AEAD (T-156 gives that a clear state).
  - HELLO (cleartext `device_id` and device name) is still sent to every discovered, remembered or loopback endpoint before the PAIRING abort. That `device_id` is what a spoofer replays to raise the Mac's approval dialog or a PAIRED answer; T-152 removes its host-side effect (no pre-proof `sessionStarted`).
  - Cancel after the Mac approved leaves the Mac with a key the tablet does not trust; recovery is the `PAIR_CANCELLED` text and, at worst, T-156's `KEY_MISMATCH`.

No SAS, key, token, `host_id` or host name in fields. `docs/LOGGING.md` is updated by the orchestrator: list the new lines under *Açık sorular*.

## Kabul kriterleri

All JVM criteria use a scripted fake host: a test harness that plays the host side with real crypto (as `CryptoVectorsTest` / `SecureChannelTest` do), sending a plaintext PENDING(PAIRING) or PAIRED/ACCEPTED first ack and then sealed records, and drives `ClientHandshake`, `PairKeyStore` and `SessionMachine` (plus the extracted controller decisions).

- [ ] [JVM] **Known host_id, no local confirm.** Trusted key K stored; user-initiated connection; PAIRING ack, then a sealed ACCEPTED: K is unchanged; a pending record holds the new key and code; `inputAllowed == false`; the UI is `AwaitingApproval(needsLocalConfirm = true)` and never `Connected`; only PING goes out (no STREAM_PREFS, DISPLAY_RATE, AUDIO_PREFS, FILES_INFO or input). Inbound CLIPBOARD, SETTINGS_OPEN, AUDIO_CONFIG and AUDIO_FRAME are not delivered.
- [ ] [JVM] **Unknown host_id, no local confirm.** Same sequence: no trusted key is created and the session is not ACCEPTED.
- [ ] [JVM] **Localhost WebDAV-token path (A2 §2).** File sharing READY (`FilesInfo(READY, port, token)` set on the machine). A fake host on the USB endpoint `127.0.0.1:47001` completes PAIRING and sends a sealed ACCEPTED: (a) reached through the AUTO probe or USB mode (`userInitiated = false`): the connection aborts at the PAIRING ack, nothing is stored, and **no FILES_INFO is ever queued**; (b) reached through a user-initiated connect: FILES_INFO is not queued until the user confirms locally. The FILES_INFO token never leaves the tablet to an endpoint the user did not confirm.
- [ ] [JVM] **Auto-discovered fake host (A2 §1).** A discovered Wi-Fi endpoint (and, separately, the remembered `lastWifiEndpoint`) answers PAIRING with a new `host_id` and a sealed ACCEPTED in the same write: the connection aborts before storing pending; the following ACCEPTED record is never processed; the result is `SessionUi.PairingNeedsUser(hostName, rePair = false)`; nothing is sent but HELLO. With the **stored Mac's `host_id`** the result is `PairingNeedsUser(…, rePair = true)` and the trusted key is byte-identical afterwards (overwrite/DoS path closed).
- [ ] [JVM] **User-initiated pairing.** A PAIRING ack on a connection opened with `userInitiated = false` (discovery, saved endpoint, USB/AUTO probe, wake connect) aborts before storing pending and yields `PairingNeedsUser(hostName, rePair)`; this state does not retry automatically (each retry would raise a new approval dialog on the Mac). The same ack on `start(…, userInitiated = true)` proceeds to the pending state. Automatic retries of a user-initiated start stay user-initiated until ACCEPTED, Cancel or Stop; a new PAIRING ack on such a retry replaces the pending record with the new key and code (the host also drops its earlier request, host `SessionMachine.swift:683-687`).
- [ ] [JVM] **Both orders.** Local confirm then host ACCEPTED, and host ACCEPTED then local confirm: pending is promoted (trusted = new key, pending removed); the session goes ACCEPTED with the existing action order (PING, STREAM_PREFS, DISPLAY_RATE, AUDIO_PREFS, FILES_INFO), `Connected` is emitted only then, and a STREAM_CONFIG that arrived before confirmation is buffered (latest only) and applied after it, opening video.
- [ ] [JVM] **Orphan / Parsec flow (T-043/T-044).** Drop during approval, then: (i) local confirm on the stored prompt (pending still present) → promoted, then a user-initiated connection gets PAIRED → completed with the promoted key; (ii) a connection made without confirming (e.g. "Yeniden eşleş" or "Bağlan" after the Mac approved) gets a PAIRED ack for a `host_id` with a fresh pending record → no key is derived from the pending (or an older trusted) key, no AEAD failure and no retry loop occur, the UI shows the **stored** code with the confirm prompt; after confirm the next connection completes PAIRED.
- [ ] [JVM] **Return before the Mac approved (QA-1 T-150 #1).** With a fresh pending record, and separately with only a fresh awaiting-host marker (confirmed before leaving), `start(…, userInitiated = false)` (the `onStart` reconnect, discovery, saved endpoint, USB/AUTO probe, wake) opens no connection and sends no HELLO; the UI is `StoredTrust(code, confirmed = false)` resp. `StoredTrust(null, confirmed = true)`. The connection after the user action is user-initiated: a PAIRING answer replaces pending and surfaces the new code; a PAIRED answer completes (after confirm) and clears the marker.
- [ ] [JVM] **Stale pending (QA-1 T-150 #2).** A pending record older than `PENDING_MAX_AGE` (wall clock) or dated in the future is deleted on read and never shown; stale pending + PAIRED ack → silent PAIRED with the trusted key; automatic connects are not blocked by it. Same for a stale awaiting-host marker.
- [ ] [JVM] **Cancel / timeout / REJECTED.** Cancel and timeout delete pending, leave trusted unchanged, send BYE + close if a connection is open, and end in terminal `Failed(PAIR_CANCELLED)` with no further `OpenControl` until a user start; this holds also while host-accepted-untrusted (sealed ACCEPTED already received). REJECTED before local confirm deletes pending; REJECTED after local confirm keeps the promoted key and clears the marker. A PAIRED handshake never uses an unconfirmed pending key.
- [ ] [JVM] **Timeout ownership (QA-1 T-150 #7).** The 2-min deadline advances on Tick only while `ConfirmPromptVisible(true)` is in effect (accumulated); `ConfirmPromptVisible(false)` pauses it; at expiry the machine behaves as `cancelTrust()` with `reason=timeout`.
- [ ] [JVM] **No trust revocation on a live session (QA-1 T-150 #3).** A key held (down sent) + `forgetCurrentHost()` → BYE and CloseControl are emitted before the records are removed, the machine ends Idle, and at no point is `inputAllowed == false` while the control connection that carried the down is still open.
- [ ] [JVM] **Atomic promotion.** A store whose commit fails yields `KEY_STORE_FAILED`; afterwards either the old state (trusted K, pending P) or the new state (trusted P, no pending) holds, never a mix or a half-written record.
- [ ] [JVM] `forgetCurrentHost()` removes the trusted record, the pending record and the marker of that `host_id` only (other hosts' records untouched); a `host_id` seen only in an aborted PAIRING answer is never used; it returns false when no eligible `host_id` was seen; the next PAIRED ack for that host yields `KEY_MISSING`.
- [ ] [JVM] **Secrets.** SAS, keys and tokens never appear in MbLog output (grep test over a full pairing, confirm, cancel, timeout and forget run).
- [ ] [build] `KeyValueStore` fakes outside `files:` (`InputSupportTest`, `GameModeTest`, `StreamModeTest`) and the settings adapter `MainActivity.kt:455` compile unchanged.
- [ ] [JVM] Old-contract tests are rewritten to assert "not replaced before confirmation": `CryptoVectorsTest.kt:233-245` and `SecureChannelTest.kt:113-119` (`client-android/app/src/test/kotlin/dev/matebridge/client/security/`).
